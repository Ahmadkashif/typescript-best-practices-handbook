## Claim clusters (part A)

**01 Language features**
- Consensus: avoid enums, runtime namespaces, parameter properties, `import =` and legacy decorators; use `as const` objects + unions and `erasableSyntaxOnly` (A-004, A-010, A-023, A-024, A-025, A-032, A-070). `satisfies` over `as` (A-027). `unknown` over `any`; `any` only in generic constraints/impl internals (A-031). `using`/`await using` are available for cleanup (A-006).
- Conflict: TC39 decorators are standard in TS 5.0 (A-046), but Node type stripping rejects all decorators (A-010). Resolution: ban decorators in code that runs stripped; frameworks that need them (Nest) force a transpile step.

**02 Compiler config**
- Consensus: `strict` (now the default in 6/7, A-002, A-001), plus `noUncheckedIndexedAccess`, `noImplicitOverride`, `verbatimModuleSyntax`, `isolatedModules`, `skipLibCheck`, `moduleDetection: force` (A-007, A-008, A-050, A-059). For Node: `module: nodenext` (A-016, A-017, A-030). Set `types: ["node"]` explicitly (the default is now `[]`, A-001, A-002). `rewriteRelativeImportExtensions` + `erasableSyntaxOnly` for stripping (A-005, A-010). Extend `@tsconfig/nodeXX` (A-060).
- Conflict: `noUncheckedIndexedAccess` false positives (A-051) vs safety (A-050). Resolution: enable it; use for-of/`.at()`. `exactOptionalPropertyTypes` is "too invasive" for strict (A-052) and has dependency friction (A-053). Resolution: PREFER in apps, not MUST. `verbatimModuleSyntax` vs `consistent-type-imports` overlap (A-062): use the compiler flag.

**03 Project structure / modules**
- Consensus: ESM (`"type": "module"`) with explicit extensions (A-015, A-075). Aliases via `package.json#imports` with a `#` prefix, which is native in Node and TS (A-014). tsconfig `paths` is legacy; `baseUrl` is removed in TS 7 (A-001, A-068). require(esm) is stable, so ESM-only is safe (A-048, A-049). Monorepos: workspaces + project references (A-068).
- No real conflict. CJS persists only for legacy.

**04 Type design**
- Consensus: discriminated unions + `never` exhaustiveness (A-047, A-063); branded types for IDs/validated values (A-026); parse don't validate (A-019); no in-domain sentinels (A-033); a single source of truth for runtime and static types (A-034); `type` by default, `interface` for extension (A-028); explicit return types on exported functions (A-029, A-059).
- Minor conflict: `interface` is faster per the perf wiki (A-059) vs "type by default" (A-028). Resolution: type by default; interface for object hierarchies/hot paths.

**05 Error handling**
- Consensus: throw only `Error` instances, chain with `cause` (A-038, A-074); split operational from programmer errors and crash on the latter (A-039). Expected domain failures are better as values/Results (A-036, A-054, A-055, A-056).
- Conflict: Result-everywhere (A-036, A-054) vs pragmatic exceptions (A-039, A-074) vs full Effect (A-037, A-069). Resolution: a small in-house `Result` for expected domain failures; typed `AppError` exceptions for the HTTP boundary/infra; programmer errors crash. Effect is AVOID-by-default (paradigm cost). The 300x perf claim (A-054) is a microbenchmark and matters only on hot paths.

**08 Async**
- Consensus: no floating promises (A-021, A-040); `await using` for resource cleanup (A-006); AsyncLocalStorage is now cheaper in Node 24 (A-065).

**09 Validation/config**
- Consensus: validate env at startup at runtime, not just by type augmentation (A-058); load .env via `--env-file`/`process.loadEnvFile`, so dotenv is unneeded (A-012); parse at the boundary (A-019, A-034); ts-reset makes JSON `unknown` (A-061).

**12 Testing**
- Consensus: Vitest is the default TS runner (A-043, A-057, A-072); node:test is viable for zero-dep libs (A-011).
- Conflict: node:test (zero deps, stable) vs Vitest (DX, ecosystem). Resolution: Vitest for apps, node:test acceptable for small libs.

**13 Tooling**
- Consensus: typed linting is worth the cost (A-020); `recommended-type-checked` baseline (A-022); flat config only (ESLint 10, A-041).
- Conflict: typescript-eslint cannot use TS 7 (A-042, A-067) vs Biome's type-aware linting without tsc (A-040, at ~75% recall on floating promises). Resolution: typescript-eslint + `@typescript/typescript6` alias now; re-evaluate when TS 7.1's API ships.

**15 Build/deploy**
- Consensus: Node runs erasable TS natively (stable in 24.12+/25.2+, A-009, A-010, A-064). It never typechecks, so `tsc --noEmit` stays in CI (A-009, A-066). TS 7 gives 8-12x faster checks (A-001, A-044, A-067).
- Open: ship `.ts` with stripping vs compile to `.js`. Neither is contradicted. Stripping disallows node_modules TS (A-010) and adds startup cost (a measurement is needed in phase-3/bench).

**17 Security**
- Permission model is stable but only a "seat belt", not a sandbox (A-013).

**18 Dependencies**
- Libraries: ESM-only is viable (A-049); verify types with attw (A-018, A-073); `exactOptionalPropertyTypes` matters for libraries (A-053).

## Claim clusters (part B)

### 00 Principles / 01 Language features / 02 Compiler config
- **Consensus:** use only the erasable, JS-aligned subset of TS. Avoid `enum`, `namespace`, parameter properties and TS decorators (A-088 Bloomberg, reinforced by Node type stripping in part A). Use one TS version and one shared tsconfig per repo (A-088). Migrations succeed incrementally, with suppressions tracked and burned down (A-089, A-090, A-091). Project references help compiler memory at scale (A-089). TS 7 cut whole-repo check times about 3x in real projects (A-111).
- **Conflict:** big-bang single-PR migration (Stripe A-089) vs package-by-package (Yelp A-090, Bloomberg A-088). Resolution: irrelevant for greenfield. For migrations, a big-bang codemod works when one team owns the repo, and incremental migration works for federated monorepos.
- **Conflict:** nodebestpractices says "use TypeScript sparingly" (A-076) vs every large-scale report showing strong gains (A-088..A-093). Resolution: the evidence favours full strict TS. The "sparingly" advice is about avoiding type gymnastics, which belongs in 04-type-design.

### 03 Project structure
- **Consensus:** structure by business component/feature, not by technical layer (A-076, A-102). Ship ESM-only now that `require(esm)` is stable in 24.15+/25.4+ (A-143). The one hazard is top-level await.

### 04 Type design / 09 Validation, config, IO
- **Consensus:** parse at the boundary into trusted types (A-121). Validate env at startup and fail fast (A-119, A-120). Use Standard Schema to stay decoupled from the validator (A-116). Zod 4 is fast enough for server APIs and has the largest ecosystem (A-079). Valibot wins on bundle size and startup, which matters mostly at the edge or in the client (A-115). ArkType/TypeBox (compiled) are fastest at runtime (A-118, A-115).
- **Conflict:** Zod vs TypeBox for Fastify. TypeBox is JSON-Schema native, so Fastify compiles it with Ajv and OpenAPI comes free. Zod has more DX and ecosystem and now emits JSON Schema (`z.toJSONSchema`, A-079), and an official type provider exists (A-117). Resolution: either is valid. Pick by whether the team prefers JSON Schema as source of truth (TypeBox) or one validator across the stack (Zod). Use the rubric/bench in phase 3.
- **Conflict:** NODE_ENV-per-environment vs "NODE_ENV=production everywhere + explicit flags" (A-119 vs common practice). Resolution: follow A-119 and A-120 with explicit config keys.

### 05 Error handling
- **Consensus:** separate operational from programmer errors and crash and restart on unknown ones (A-076). Use one shutdown path for signals and fatal errors with a force-exit timeout (A-139). Use RFC 9457 problem+json for HTTP error bodies (A-147). Hide internals from clients (A-076, A-147). Express 5 now forwards rejected promises (A-138).

### 06 Design patterns / 07 Architecture
- **Consensus:** use a composition root with factory functions and partial application, no container required (A-101). Ports/adapters exist for testability (A-103). Start as a (modular) monolith and extract services only on concrete triggers (A-104, A-148). Use the outbox for DB+event atomicity, with idempotent consumers (A-113).
- **Conflict:** layered/hexagonal everywhere (A-103) vs vertical slices (A-102). Resolution: vertical feature modules at the top level, with ports/adapters only at real I/O seams (DB, external APIs), not for every class.
- **Conflict:** NestJS DI/decorators for big teams (A-142) vs function composition (A-101). Resolution: decorators/parameter properties conflict with erasable-only TS (A-088 plus part A). AVOID Nest for new services under this guide, and record it in the ADR.

### 08 Async & concurrency
- **Consensus:** never block the loop. No `*Sync` APIs in servers. Watch for ReDoS and huge `JSON.parse` (A-078, A-130). Workers only for synchronous CPU work, always pooled (Piscina) with backpressure (A-136). Use `stream/promises.pipeline` and respect backpressure (A-125). AsyncLocalStorage is acceptable (~7% overhead) for request context (A-135).

### 10 Data access
- **Consensus:** keep pools small. Per-process max × instances must stay under DB max connections. Use a proxy such as pgBouncer for autoscaling (A-105, A-106). Use generated, versioned SQL migrations in prod (no `push`) (A-111). Use expand/contract for zero-downtime schema changes (A-114). Wrap multi-step writes in transactions and use the outbox for events (A-113).
- **Conflict:** Drizzle vs Prisma vs Kysely (A-107..A-112). Resolution criteria: SQL transparency, no codegen step, type-check cost and runtime deps. Drizzle/Kysely lead on transparency and no binary. Prisma 7 removed Rust, but `prisma@latest` is an 8.0 RC (unstable channel) on 2026-10-06. Decide in phase 4.

### 11 HTTP APIs
- **Consensus:** Fastify is the fastest mainstream Node framework (50.4k vs Express 27.5k req/s, about 1.8x, A-077), but the gap shrinks to near zero once a DB is involved (pkgpulse aggregator snippet, low credibility, not logged as a row; to be measured in phase-3/bench). Set request size limits and timeouts (A-080, A-146). Set keepAliveTimeout above the LB idle timeout (A-137). Use rate limiting with a shared store across instances (A-144, A-145). Use security headers via helmet (A-129). Use load shedding with 503 (A-140).
- **Conflict:** Hono (Web-standard, multi-runtime, A-149) vs Fastify (Node-native, plugin encapsulation, schema compilation). Resolution: Node-only backend means Fastify. Hono only when edge or multi-runtime portability is a hard requirement.

### 12 Testing
- Ports/adapters justify in-memory adapters for unit tests (A-103). Other testing evidence is in part A.

### 14 Performance
- **Consensus:** measure first (`--cpu-prof`, flame graphs) (A-094, A-095, A-130). Use `undici.request` for hot-path outbound HTTP (about 3x fetch, A-100), and always consume or cancel bodies. Monitor ELU and event-loop delay (A-150, A-140). Full OTel auto-instrumentation can cost about 80% throughput, so instrument selectively (A-135).

### 15 Build & deploy
- **Consensus:** multi-stage builds, prod-only deps, non-root, pinned base digest, .dockerignore, run `node` directly (not `npm start`) with an init or signal handling, HEALTHCHECK/probes (A-081, A-083, A-128). Liveness must not check dependencies, readiness can, and startup probes cover slow boots (A-123). Handle the SIGTERM→endpoint-removal race with a readiness flip plus drain delay (A-087).
- **Conflict:** base image. Snyk recommends `bookworm-slim` with distroless as second choice and warns that Alpine/musl is experimental (A-133). Distroless is smallest with no shell (A-126). Chainguard markets ~80MB zero-CVE (A-134). Resolution: build on `node:24-<debian>-slim`, run on `gcr.io/distroless/nodejs24-debian13:nonroot` if it boots cleanly, otherwise slim. AVOID Alpine for production (musl). Measure image size in phase 3.

### 16 Observability
- **Consensus:** pino NDJSON to stdout, transports off-thread, redaction, child loggers with request ids (A-084, A-085, A-122). Load OTel via `--import`/`--require` before app code (A-086, A-124). Prefer metrics + profiling and add traces selectively (A-135).

### 17 Security
- **Consensus:** validate input, limit body size, add rate limits, helmet headers, no stack traces to clients (A-080, A-129, A-146). `npm install` is RCE: use `--ignore-scripts`, a cooldown (`min-release-age`), `npm ci`, lockfile linting and minimal deps (A-082, A-132, A-146). Publish via OIDC trusted publishing with provenance (A-127). Pin Actions to SHAs with least-privilege tokens (A-141). Harden containers: cap-drop, read-only fs, no-new-privileges (A-128). The Permission Model is a seat belt, not a sandbox (A-099).

### 18 Dependencies
- **Consensus:** automated, grouped updates with a release-age delay (Renovate `minimumReleaseAge`, A-131). Treat every new dependency as attack surface (A-082). Use one version of each dependency across the monorepo (A-088).
